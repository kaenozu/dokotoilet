# 熊谷OD126件の評価取り直しプロンプト（手動調査化）

熊谷市オープンデータ由来の126件は現在すべて設備推定値（`estimated`）。
ChatGPT（Deep Research またはブラウジング有効）で1件ずつ Google Maps の
listing を探して調査し直し、手動調査データ（`survey`）へ格上げする。

## 使い方

1. 下の「共通指示」と「施設リスト（バッチN）」をセットで貼る
   （126件一括は無理なので、14件×9バッチに分割。各バッチ1セッション）
2. 出力JSONを保存する（例: `inputs/reevaluate-od-batch1.json` … batch9 まで）
3. 全バッチ揃ったら既存入力と合わせて再生成する:
   ```bash
   bun scripts/manual-import/run.ts --in scripts/manual-import/inputs/shibuya-01.json --in scripts/manual-import/inputs/kumagaya-manual-01.json --in scripts/manual-import/inputs/kumagaya-02.json --in scripts/manual-import/inputs/reevaluate-od-batch1.json --in scripts/manual-import/inputs/reevaluate-od-batch2.json --in scripts/manual-import/inputs/reevaluate-od-batch3.json --in scripts/manual-import/inputs/reevaluate-od-batch4.json --in scripts/manual-import/inputs/reevaluate-od-batch5.json --in scripts/manual-import/inputs/reevaluate-od-batch6.json --in scripts/manual-import/inputs/reevaluate-od-batch7.json --in scripts/manual-import/inputs/reevaluate-od-batch8.json --in scripts/manual-import/inputs/reevaluate-od-batch9.json
   ```
4. 生成後に `git diff --stat src/data/googleSeed.ts` で件数を確認する

## 仕組み（重複の扱い）

- 調査結果は `google-{place_id}` として `googleSeed.ts` に入る
- アプリ起動時の結合（`mergeSeedLists`、半径30m）で、同じ場所の既存 `od-*`
  エントリは自動的に落とされ、設備フラグはOR統合される。つまり調査済みの
  OD施設は推定値から調査値へ自然に置き換わる。取込側で何も消す必要はない
- 逆に言うと、listing が見つからなかった施設は `od-*` のまま残る（推定値のまま）

## 共通指示（ここから貼る）

あなたは公衆トイレ調査のリサーチャーです。「きれいトイレ」アプリに登録済みの
熊谷市の公衆トイレについて、下の施設リストを1件ずつ調べ直してください。
現在は設備からの推定値しかなく、Google Maps の実情報で評価を付け直すことが目的です。

### 調査手順（1件ごと）

1. 施設名＋住所＋座標で Google Maps 上の listing を探す
2. トイレ単体の listing があればそれを使う。無い場合は下の「listing が無い場合」ルールに従う
3. 口コミを新しい順・評価順の両方で読み、トイレの清潔さに関する直近の「傾向」を要約する
   （例：「直近の口コミN件中M件が清潔さに好意的」）
4. 営業時間・設備（ウォシュレット・多機能・ベビー・パウダー・24時間）は listing・公式サイトで裏取りする
5. listing に表示される口コミ総件数を記録する（0件なら0と書く）

### listing が無い場合（公園内トイレに多い）

- トイレ単体の listing が無い施設は JSON に含めず、最後に「対象外リスト」として別に列挙する
  （施設名＋理由1行。「公園全体の口コミしか無い」「listing 自体が無い」等）
- 公園自体の listing しか無い場合、その口コミ全体でスコアを付けないこと。
  ただし公園の口コミ文中にトイレへの言及があれば、その傾向だけを根拠に使ってよい。
  この場合 `confidence` は `"low"` または `"medium"` にし、`scoreBasis` に
  「公園口コミ内のトイレ言及が根拠」と明記する
- 近隣の無関係な施設（コンビニ・駅など）の listing を当てはめないこと

### スコア基準（1.0〜5.0）

- 5.0: 複数口コミで「とても綺麗」等、否定的言及なし
- 4.0: おおむね清潔、一部指摘あり
- 3.0: 可もなく不可もなく
- 2.0: 汚い・臭い等の指摘が複数
- 1.0: 利用を避けるべきとの声が支配的
- 情報不足で判定不能な場合は `cleanlinessScore` に `null` を入れ、`confidence` を `"low"` にする
  （取込時に中立値3.0＋要確認メモになる。安易な3.0入れは禁止）

### 厳守ルール

- 実在しない施設を作らない。`googleMapsUrl` は実際に開いた listing の URL を使う
- `name` は下表のOD名のまま使う（変えない）。`category` も下表のまま使う
- 口コミ本文の転載は禁止（原文ママはもちろん、ほぼ同一の書き換え・翻案も不可）。
  要約は必ず自分の文章で書き、件数と傾向は `scoreBasis` に記録する
- `scoreBasis` には必ず直近口コミの件数と傾向を書く
- 次元別スコア（`subScores`：便器・床の清潔さ / におい・換気 / 石鹸・ペーパー・除菌 / 広さ・快適さ）を
  分かる範囲で1.0〜5.0で付ける。不明な次元は `null`（総合スコアにフォールバックされる）
- `surveyedAt` に調査日（YYYY-MM-DD）を入れる
- 設備は `true`（あり）/ `false`（なし）/ `null`（未確認）の3値。未確認を `false` にしない
- 住所・座標は listing 記載のまま。推測で補完しない。不明は `null`
  （取込時に Nominatim 補完が効く。ただしOD由来の座標があるため、大きくずれる場合だけ申告する）
- 出力は下記スキーマのJSONのみ（コードブロック1つ）。対象外リストとカバレッジの限界
  （調べ切れていない点3行以内）は JSON の後に別に書く
